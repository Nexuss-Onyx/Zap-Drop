# Capacitor Application Engineering

Operate as the owner of the complete Capacitor delivery lifecycle. Inspect the repository before changing it, preserve existing product behavior and visual assets, make the smallest compatible change, build from a clean state, verify the native artifact, and report reproducible commands and evidence.

## Operating contract

- Work from the repository root. Do not assume Manus, a particular IDE, a hosted CI provider, or a specific shell.
- Treat `package.json`, lockfiles, `capacitor.config.*`, native project files, and existing release scripts as the source of truth. Never silently replace a package manager or lockfile.
- Prefer the project’s package manager: `bun.lock` → Bun, `pnpm-lock.yaml` → pnpm, `yarn.lock` → Yarn, `package-lock.json` → npm. If several exist, inspect scripts and recent history, then use the least disruptive choice.
- Do not overwrite generated native files casually. Determine whether a file is generated by Capacitor, a plugin, or the app. Make durable changes in the source configuration or regeneration script when possible.
- Preserve existing logos, favicons, splash artwork, animations, colors, and layout unless the task explicitly requests a redesign. Reuse canonical assets instead of inventing replacements.
- Never commit secrets, keystores, passwords, access tokens, `.env` files, or machine-local files. If a credential is exposed, stop using it, recommend revocation, and remove it from logs and remotes.
- Treat release publication, signing-key changes, force-pushing tags, deleting assets, and production deployment as consequential. Obtain explicit confirmation when the exact payload has not already been approved.

## Delivery workflow

Follow these phases in order. Skip a phase only when its entry criteria are already proven and record why.

1. **Reconnaissance**
2. **Compatibility plan**
3. **Implementation**
4. **Native synchronization**
5. **Build and static validation**
6. **Device/emulator validation**
7. **Signing and artifact inspection**
8. **Release and rollback plan**
9. **Final report**

### 1. Reconnaissance

Run safe read-only checks first:

```bash
pwd
git status --short --branch
find . -maxdepth 2 -type f | sort
cat package.json
cat capacitor.config.json 2>/dev/null || true
```

Inspect, as applicable:

- package manager and lockfiles;
- Capacitor core, platform, CLI, and plugin versions;
- `webDir`, `appId`, `appName`, URL scheme, server URL, and embedded-vs-remote content;
- `android/variables.gradle`, `android/app/build.gradle`, manifests, themes, resources, Gradle wrapper, and signing configuration;
- `ios/` deployment target, schemes, entitlements, bundle identifier, and signing settings;
- web build scripts, environment variables, API endpoints, CSP, asset paths, and service workers;
- release scripts, CI workflows, Git tags, GitHub/GitLab release conventions, and existing artifacts.

Search for compatibility and release hazards:

```bash
rg -n "minSdk|targetSdk|compileSdk|deploymentTarget|signing|keystore|gradlew|cap sync|cap copy|webDir|server.url|splash|icon|favicon" .
```

Before editing, record the current branch, latest release/tag, package ID, version code, version name, and whether the working tree is clean.

### 2. Compatibility plan

Map the user’s requested device range to platform API levels before choosing versions. Do not lower `minSdk` independently of the Capacitor major version and every native plugin.

For Android, verify all of the following:

- Capacitor Android’s official minimum API for the selected major version;
- every plugin’s minimum API and transitive AndroidX requirements;
- compile SDK and target SDK required by that Capacitor major version and current store policy;
- Java, Gradle, Android Gradle Plugin, Kotlin, Android Studio, and Build Tools compatibility;
- whether the device is Android 5.0/API 21 or Android 5.1/API 22; these are not interchangeable.

For iOS, verify the Capacitor major version’s Xcode and deployment-target requirements, then check plugin deployment targets and architecture support.

When a requested range is unsupported, explain the exact boundary and choose one of these paths:

1. upgrade the device requirement;
2. downgrade the Capacitor/native dependency line as a coordinated set;
3. replace or remove incompatible plugins;
4. implement a separate legacy build only when maintenance and security costs are acceptable.

Never claim support from `minSdk` alone. Prove it by resolving dependencies, compiling, inspecting the artifact manifest, and testing on a representative device or emulator.

### 3. Implementation

Make changes in this order:

1. update direct dependencies with the project package manager;
2. update the lockfile in the same change;
3. update Capacitor configuration and web build output only when required;
4. update native project variables and durable source files;
5. regenerate native projects with `npx cap sync <platform>` or the equivalent project command;
6. review the generated diff and restore unrelated changes.

For assets:

- identify the canonical source asset first, usually `public/favicon.svg`, a brand SVG, or an existing component;
- preserve aspect ratio with `centerInside`/contain semantics; do not stretch a square mark into a rectangular canvas;
- use a black or explicitly requested background consistently across density buckets and orientations;
- mirror an existing web animation by translating its actual states and timing, not by inventing an unrelated animation;
- keep a deterministic generator script for rasterized assets when multiple Android densities or animation frames are needed;
- remove obsolete assets only after searching all references and verifying resource compilation.

For splash screens, distinguish the Android 12+ system splash API from the pre-12 theme fallback. Configure both where the project supports both generations. Keep the post-splash theme visually consistent with the launch screen.

### 4. Native synchronization

Build web assets before copying them into native projects:

```bash
<package-manager> run build
npx cap sync android
# or
npx cap sync ios
```

Check that `webDir/index.html` exists after the web build. Inspect the synchronized native diff:

```bash
git status --short
git diff -- android ios package.json <lockfile>
```

Never use a remote development URL in a release artifact unless the task explicitly requires it. Confirm that production API URLs, cleartext policy, network security config, and CSP are intentional.

### 5. Build and static validation

Use the repository’s scripts first. If no release script exists, use the platform-native command with the project wrapper:

```bash
# Android
JAVA_HOME=/path/to/java-17 bash android/gradlew -p android assembleRelease

# iOS (macOS only)
xcodebuild -workspace ios/App/App.xcworkspace \
  -scheme App -configuration Release \
  -sdk iphoneos -archivePath build/App.xcarchive archive
```

Use Java and SDK versions required by the selected Capacitor line. If a wrapper lacks executable permission, invoke it through `bash` or fix the tracked mode intentionally.

Run, as available:

```bash
<package-manager> run lint
<package-manager> run test
<package-manager> run typecheck
```

For Android, ensure required SDK packages are installed and licenses are accepted. Do not hide build errors with `--offline`, dependency substitution, or arbitrary `minSdk` overrides.

### 6. Device/emulator validation

Prefer a real device for old Android behavior. Otherwise create an emulator matching the minimum API and one current API.

Android smoke test:

```bash
adb devices
adb install -r path/to/app.apk
adb shell am force-stop com.example.app
adb shell monkey -p com.example.app 1
adb logcat -c
adb logcat -d | rg -i "FATAL EXCEPTION|AndroidRuntime|Capacitor|WebView"
```

Validate at minimum:

- install and launch from a clean state;
- cold start and warm start;
- splash background, icon scale, and transition;
- orientation and window resize behavior;
- web assets load without blank screen;
- API calls, authentication, storage, deep links, and permissions;
- back button, keyboard, file chooser, and external intents where relevant;
- behavior on the requested minimum API and a current API.

If no device is available, state that limitation explicitly and compensate with manifest/resource inspection and build-time checks.

### 7. Signing and artifact inspection

Do not publish an unsigned release. Determine whether the project has an existing production keystore or Apple signing identity. Never generate a replacement production key without explicit approval because Android updates require the same signing identity.

Android inspection:

```bash
apksigner verify --verbose --print-certs app-release.apk
aapt dump badging app-release.apk | rg "package:|sdkVersion|targetSdkVersion"
sha256sum app-release.apk
```

Check that:

- package/application ID is correct;
- version code and version name are intentional;
- `sdkVersion` matches the promised minimum;
- target SDK is policy-compliant;
- required permissions and exported components are expected;
- signature verification succeeds;
- artifact checksum is recorded.

For Android App Bundles, inspect with `bundletool` when available. For iOS archives, validate signing, provisioning, entitlements, architectures, and export options.

### 8. Release and rollback plan

Before any external release action, prepare:

- exact commit and tag;
- release title and notes;
- artifact filename and checksum;
- compatibility statement;
- migration/install note, including signing-key implications;
- rollback or replacement procedure.

Prefer immutable version tags. If the user explicitly requests replacing an existing release, update the source commit first, then update the tag and asset together, and verify that the release page, tag, commit, asset URL, size, and checksum all agree.

Use APIs or CLIs without placing tokens in remotes, shell history, committed files, or logs. Delete temporary credential files after use. Never upload debug APKs or unsigned artifacts.

### 9. Final report

Report:

- what changed and why;
- exact supported OS/API boundary;
- files changed;
- commands run;
- build and test results;
- artifact path, public URL, and checksum if released;
- known limitations and required user action;
- whether the working tree is clean.

Do not say “supports older Android” without naming the API level. Do not say “release successful” until the public artifact has been fetched or API-verified and its checksum matches the local file.

## Failure diagnosis

### “App not installed”

Check, in order:

1. device API is below `minSdkVersion`;
2. APK is unsigned or signature conflicts with an installed package;
3. package ID/version/signature conflicts with an existing installation;
4. APK is an incompatible ABI or split artifact;
5. manifest has invalid exported components or permissions;
6. device storage, installer policy, or unknown-sources policy blocks installation.

Collect the real installer error with `adb install -r -d app.apk` and `adb logcat`; do not guess from the UI message.

### Blank screen or immediate crash

Check web assets exist in `android/app/src/main/assets/public` or the iOS equivalent, `capacitor.config.*` points to the correct directory, API URLs are reachable, WebView requirements are met, and the first fatal exception in logcat is addressed before secondary errors.

### Splash is stretched or wrong

Inspect all density/orientation resources and theme references. Use a square source with proportional scaling, black padding when requested, and one canonical asset. Confirm no old `splash.png`, invented face asset, or generated resource remains referenced.

### Build fails after a Capacitor downgrade

Reconcile the whole matrix: Capacitor core/platform/CLI/plugins, AndroidX versions, Gradle wrapper, AGP, Java, compile SDK, target SDK, and Cordova Android. Re-run `cap sync`, remove only safe generated build directories, and rebuild. Do not mix major Capacitor lines.

## Completion gate

Do not finish until all applicable checks pass:

- repository state inspected before edits;
- dependency and lockfile changes are consistent;
- web assets build and synchronize;
- native release build succeeds;
- artifact manifest and signature are inspected;
- requested minimum API is proven;
- requested device smoke test is performed or explicitly unavailable;
- no secrets or machine-local files are committed;
- release metadata and checksum match the published artifact when publishing;
- final report contains reproducible commands and limitations.
